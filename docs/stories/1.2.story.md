## Story

**As a** dev,
**I want** o schema Supabase para protocolos e produtos (preços, ativos, imagens, métricas de prova social) criado e populado com os dados reais do brief,
**so that** as páginas renderizem dados reais em vez de mocks.

## Acceptance Criteria

1. Tabelas `products`, `protocols` e `protocol_products` criadas no Supabase com campos para nome, preço avulso, preço assinatura, categoria, ativos, imagem, métricas de prova social.
2. Seed contém os 3 protocolos e 5 produtos avulsos do brief com valores corretos, incluindo os relacionamentos N:N corretos em `protocol_products`.
3. Camada de dados (`lib/data/catalog.ts`, Supabase client) lê e retorna os dados seedados corretamente.
4. Nenhuma referência à palavra "Kit" nos dados seedados.

### Technical Constraints

- **Escopo desta migration é só catálogo** — `orders`/`subscriptions` (Story 2.2) e `leads` (Story 1.3) ganham migrations próprias depois, no commit da story que primeiro escreve nelas. Não antecipar essas tabelas aqui [Source: schema-design.md Seção 10/14 — corrigido nesta sessão, era autocontraditório antes].
- **`stripe_price_id*` sem valor real ainda, mas colunas são `NOT NULL, UNIQUE`** (schema-design.md Seção 4/7) — usar placeholder **único por linha** derivado do slug (ex: `'pending:' || slug`), nunca uma string genérica repetida entre produtos/protocolos (violaria `UNIQUE`) e nunca `NULL`/vazio. Story 2.1 substitui via `UPDATE` quando os Products/Prices reais existirem no Stripe.
- **Fonte dos dados do seed:** catálogo real (5 produtos, 3 protocolos, preços, ativos, composição de cada protocolo) está no Project Brief original fornecido pelo usuário no início da sessão de PRD — não reinventar valores.

### Testing

[Source: architecture.md Seção 14]

- Teste de integração: `lib/data/catalog.test.ts` — `getProducts()`/`getProtocols()` retornam os valores seedados corretos (contagem, preços, categoria).
- Teste de constraint: seed que violasse um `CHECK`/`UNIQUE` deve falhar a migration — validar manualmente que os dados reais passam antes de aplicar em qualquer ambiente.

### Completion Notes List

- **Sem Docker neste ambiente** — não deu pra rodar `supabase db start`/dry-run local. Migration foi escrita, revisada manualmente (linha a linha contra schema-design.md) e aplicada direto no projeto dev/preview real via `supabase db push`, que já validou todos os constraints na aplicação (sucesso = prova de que o DDL está correto).
- **Sem `SUPABASE_ACCESS_TOKEN` no meu ambiente de execução** — CLI do Supabase não faz OAuth por navegador (diferente de Vercel/GitHub), só aceita token direto. Não coloquei token no meu contexto (mesma categoria de credencial sensível das minhas regras) — o usuário rodou `supabase link`/`supabase db push` no terminal dele mesmo, eu só preparei os comandos e as migrations.
- **Achado sério, resolvido antes de aplicar qualquer coisa:** o primeiro projeto Supabase que o usuário passou (`rqopfjczhyrjauznxztn`) tinha o badge **PRODUCTION** no dashboard e já continha tabelas com dado real (`protocols` com nomes tipo "Complete"/"Reconstruct", `profiles`, `subscriptions`, `user_diagnoses`) — schema completamente diferente do nosso, claramente do projeto TRIA antigo (mesmo padrão do repo GitHub `TRIA-Ecommerce` descoberto na Story 1.1). Parei antes de rodar `db push` nele, confirmei com o usuário, e ele criou um projeto novo (`ocoohbujwkbsbiyljhdy`) especificamente pra dev/preview — o projeto antigo ficou intocado.
- **Preço anual dos protocolos não estava no brief** (só "anual com desconto adicional", sem número) — perguntei ao usuário em vez de inventar um percentual de desconto. Confirmado: Opção A (paga 10 meses, leva 12) — Cuidados Diários R$1.350, Ritual de Autoridade R$2.490, Implante & Alopecia R$2.090.
- **`.env.local` não é carregado pelo Next.js quando `NODE_ENV=test`** (decisão de design do próprio Next, documentada) — Jest seta `NODE_ENV=test` automaticamente, então a integração real falhava com "URL and Key required" até eu criar `.env.test.local` (mesmo conteúdo, gitignorado, carregado nesse cenário específico).
- **`fetch is not defined`** — jsdom (ambiente padrão do Jest) não expõe `fetch` global; `@supabase/supabase-js` precisa dele. Corrigido com `@jest-environment node` no topo do arquivo de teste (correto semanticamente também — o teste não toca DOM).
- **Timeout padrão do Jest (5s) curto demais** pra chamada de rede real — ajustado com `jest.setTimeout(15000)`, específico deste arquivo de teste de integração.
- **`npm audit` — 2 vulnerabilidades novas surgiram ao instalar `@supabase/*`** (high em `sharp`, dependência transitiva do próprio Next.js pra `next/image`, não do Supabase): diferente da postcss aceita na Story 1.1, essa tinha fix real sem quebrar nada — bump de patch do Next (16.2.10→16.2.11, resolveu vários CVEs reais de SSRF/DoS/bypass também) + `overrides` cirúrgico forçando `sharp@^0.35.0`. Build/test confirmados passando depois.
- **Não criei `lib/supabase/server.ts`** como arquivo separado da story original — Architecture já especificava esse helper (Seção 8.4/9.2) mas nenhuma story anterior o criou; consultei a doc oficial do `@supabase/ssr` via Context7 (não inventei o padrão) antes de escrever, incluindo o padrão de `setAll` em try/catch específico pra Server Components.
